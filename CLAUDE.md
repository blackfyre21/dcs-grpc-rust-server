# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

DCS-gRPC: a gRPC server that lets network clients interact with a running DCS World mission. The Rust code compiles to a Lua C module (`dcs_grpc.dll`, `crate-type = ["cdylib"]`) that DCS loads via `require`. Most RPCs are ultimately executed by Lua scripts inside DCS's scripting environments. The target platform is Windows (Lua 5.1 headers and `lua.lib` are vendored in `src/lua5.1/`; `.cargo/config.toml` wires them up).

## Commands

```powershell
cargo build                                   # builds dcs_grpc.dll (also regenerates lua/DCS-gRPC/version.lua)
cargo build --features hot-reload             # hot-reload build; then copy the dll (see below)
copy target/debug/dcs_grpc.dll target/debug/dcs_grpc_hot_reload.dll   # `make build` does both steps
cargo test --workspace                        # all tests (most live in stubs/src/lib.rs)
cargo test -p dcs-grpc-stubs test_enum_deserialization   # single test
cargo clippy --workspace -- -D warnings       # CI lint (warnings are errors)
cargo fmt -- --check                          # CI formatting check
luacheck ./lua                                # CI Lua lint
protolint lint protos/.                       # CI proto lint
cargo run -p dcs-grpc-repl                    # Lua REPL against a running mission (needs evalEnabled; localhost:50051)
```

If `cargo build` fails with `LNK1104: cannot open file`, a running DCS mission has the DLL locked. Exit the mission (not DCS) and rebuild.

Manual testing against a running server uses grpcurl, e.g.:
`grpcurl.exe -plaintext -import-path ./protos -proto ./protos/dcs/dcs.proto -d '{}' 127.0.0.1:50051 dcs.mission.v0.MissionService/StreamEvents`

## Workspace layout

- root crate `dcs-grpc` (`src/`): the DLL. It contains the tonic server, the RPC service impls, and the Lua-facing exports.
- `stubs/`: generated gRPC/prost types from `protos/dcs/**.proto` (via `stubs/build.rs` using bundled protoc). Each module is just `tonic::include_proto!`, plus hand-written serde helpers where Lua's shape differs from the proto.
- `srs/`: SimpleRadioStandalone client (voice/messages codecs) used for transmitting audio.
- `tts/`: text-to-speech providers (AWS, Azure, Google Cloud, Windows).
- `repl/`: CLI that calls the custom `Eval` RPC.
- `lua/DCS-gRPC/`: Lua side that runs inside DCS. `lua/Hooks/DCS-gRPC.lua` is the hook-environment entry point.

## Architecture: how a request flows

1. A client calls a tonic service. Services are registered in `src/server.rs`. Nearly all are implemented on `MissionRpc`. `HookService` uses `HookRpc`. `SrsService` uses `Srs`.
2. The impl in `src/rpc/<service>.rs` usually just does `self.request("methodName", request).await`. This serializes the proto request with serde (camelCase) and enqueues it on a `dcs_module_ipc::IPC` queue.
3. In DCS, `lua/DCS-gRPC/grpc.lua` polls `grpc.next(env, handleRequest)` on a timer (mission env = 1) or on each simulation frame (hook env = 2). The throughput is limited by `throughputLimit`. `next` in `src/lib.rs` pops a request and calls the Lua handler.
4. The handler dispatches to `GRPC.methods[methodName]`, which is defined in `lua/DCS-gRPC/methods/*.lua`. It returns `GRPC.success(result)` or an error helper such as `GRPC.errorNotFound(msg)` or `GRPC.errorInvalidArgument(msg)`. The error `type` maps to a gRPC status in `to_status` (`src/rpc.rs`).
5. The Lua result is deserialized via serde into the proto response type.

DCS events go the other way. `world.addEventHandler` → `GRPC.onDcsEvent` (`methods/mission.lua`) builds a table → `grpc.event(...)` → it is deserialized into `StreamEventsResponse` (tagged by `type`, camelCase variant names) and broadcast to `StreamEvents` subscribers. `StreamUnits` (`src/stream.rs`) is synthesized server-side by polling other RPCs plus birth/dead events.

### Adding or changing an RPC requires touching all layers

- `.proto` in `protos/dcs/<service>/v0/` (document with protoc-gen-doc comments)
- Rust impl in `src/rpc/<service>.rs` (the trait method is generated by tonic)
- Lua impl `GRPC.methods.<camelCaseName>` in `lua/DCS-gRPC/methods/<service>.lua`
- `STATUS.md` (DCS API parity checklist) and the `Unreleased` section of `CHANGELOG.md`
- New event types: add a branch to `GRPC.onDcsEvent`. Events that are not handled get logged as unimplemented.

### Serde / proto conventions to be aware of

- `stubs/build.rs` adds `Serialize/Deserialize` + `rename_all = "camelCase"` to every generated type. Per-type overrides also live there: `serde(from = "...Intermediate")` for `Unit`, `Weapon`, and transform responses, plus `proto_struct` for free-form `google.protobuf.Struct` fields. When adding fields that Lua sends in a non-proto shape, extend these intermediates (e.g. `stubs/src/common.rs`, which computes orientation/velocity from raw vectors) and not the Lua side.
- **Enum offset:** gRPC enums reserve 0 for `UNSPECIFIED`, so Lua adds `+ 1` to DCS enum values (coalition, categories, etc.) when sending them. It subtracts 1 when receiving. Keep this consistent in any new Lua code.
- Lua values reach Rust as JSON-like tables. `stubs/src/lib.rs` tests deserialize JSON strings that mimic Lua output. This is the main place to add tests.

### Runtime details

- `build.rs` writes `lua/DCS-gRPC/version.lua` and embeds hashes of every Lua file. At startup `src/integrity.rs` verifies that the DLL version and the Lua file hashes match, unless `integrityCheckDisabled = true` in `Saved Games\DCS\Config\dcs-grpc.lua`. Set that flag for local Lua edits without rebuilding.
- `hot-reload` feature: the module exported as `dcs_grpc_hot_reload` (`src/hot_reload.rs`) dynamically loads `dcs_grpc.dll` on `start` and unloads it on `stop`. That lets you rebuild the real DLL between missions without restarting DCS. `grpc-mission.lua` prefers `dcs_grpc_hot_reload` if it is present.
- The exported functions in `src/lib.rs` run on DCS's thread. `simulation_frame` runs every frame and must stay lock-free. `event` must never return an error to Lua because that can crash DCS, so it only logs.
- Config comes from the Lua `GRPC` table (built by `grpc-mission.lua` / the hook from `Config/dcs-grpc.lua`) and is passed to `start` as `src/config.rs::Config`. Optional `X-API-Key` auth is in `src/authentication.rs`.
- Logs go to `Saved Games\DCS...\Logs\gRPC.log`. Lua logs also appear in `dcs.log` with the `[GRPC]` / `[GRPC-Hook]` prefixes.

## Contribution conventions (from CONTRIBUTING.md)

- Keep the gRPC interface simple and consistent for clients, even at the cost of server complexity. Follow ED API naming by default, but renaming for clarity is fine.
- Write multi-line commit messages (50-char imperative summary, wrapped body) and squash into logical atomic commits.
- Update `CHANGELOG.md` under `Unreleased`.
